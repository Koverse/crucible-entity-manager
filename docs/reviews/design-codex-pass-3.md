## Findings

1. **Critical — §5.3/D11: a failed PUT does not establish that a head is missing.** The design creates every ID it treats as “not found” after PUT, but `include_failed_records=True` returns records that failed validation **or** were not found. The baseline fallback similarly groups failed IDs together; it supplies no reason code. An ENTITY upsert for a validation failure could overwrite an existing head, including fields owned by another writer. Evidence: [DESIGN.md:265](docs/DESIGN.md:265), [entity_utils.py:386](src/objectApps/correlators/entity_manager/entity_utils.py:386), [entity_utils.py:632](src/objectApps/correlators/entity_manager/entity_utils.py:632). **Recommendation:** check existence for failed IDs, or obtain an API response that distinguishes not-found from validation failure. Await a successful PUT or create before releasing that key’s events.

2. **Critical — §5.7: the claimed drain bound is false.** Connect, write, read and pool timeouts are phase or inactivity limits; adding them does not cap a request’s elapsed time. The synchronous write client also configures **three transport connection retries**, which can occur inside one `to_thread` call. The controller’s separate status-code backoff loop is for async requests, not these writes. Thus a thread can survive the 20-second drain despite the 15-second budget check. Evidence: [DESIGN.md:429](docs/DESIGN.md:429), [controller.py:180](site-packages/cruciblelib/controllers/v2/controller.py:180), [controller.py:316](site-packages/cruciblelib/controllers/v2/controller.py:316), [controller.py:455](site-packages/cruciblelib/controllers/v2/controller.py:455). **Recommendation:** enforce a deadline over the entire synchronous operation, including transport retries, or explicitly allow unfinished threads and report the drain as failed. Do not infer that every thread finishes from the timeout sum.

3. **Major — §5.5: association stamps cannot safely use the stated create fallback.** The table says missing association updates are recreated with an ENTITY upsert. The fuser sends only `trackId` and `associatedPrincipalTrack`; the baseline deliberately retains failed stamps for retry, while its general fallback calls for a *full* create record when an update is sparse. Upserting the stamp alone can create an incomplete component head or overwrite a complete one in a race. Evidence: [DESIGN.md:344](docs/DESIGN.md:344), [entity_track_fuser.py:137](src/objectApps/correlators/entity_manager/entity_track_fuser.py:137), [entity_utils.py:618](src/objectApps/correlators/entity_manager/entity_utils.py:618). **Recommendation:** retry stamps after the tracker creates the component head; reserve create fallback for full head records.

4. **Major — §5.3/D2: evicting the fuser identity accumulator changes output identity.** Fused identity is the union of values seen across component tracks. After the proposed idle or LRU eviction, the next principal event contains only values observed since eviction; PUT may preserve fields on the stored head, but it cannot restore them to that event. Evidence: [DESIGN.md:82](docs/DESIGN.md:82), [DESIGN.md:259](docs/DESIGN.md:259), [entity_track_fuser.py:262](src/objectApps/correlators/entity_manager/entity_track_fuser.py:262), [entity_track_fuser.py:939](src/objectApps/correlators/entity_manager/entity_track_fuser.py:939). **Recommendation:** rehydrate the accumulator from durable state on eviction miss, or document and test the resulting loss of fused identity in events.

5. **Major — §5.5/D4: equal-time rewrites are still suppressed.** The revised tracker identity distinguishes a rewrite only when its kinematics timestamp changes. A changed measurement under the same origin UUID and timestamp is explicitly discarded as a duplicate; the fuser key inherits that limitation. Evidence: [DESIGN.md:350](docs/DESIGN.md:350), [DESIGN.md:355](docs/DESIGN.md:355). **Recommendation:** include a record revision or content fingerprint, or state this loss as a deliberate D4 behavior and test it.

6. **Minor — §§3, 5.5, 8: several summary claims overstate the body or baseline.** §3 says repeat writes must be harmless, while D10 accepts duplicate rows and competing head states; §5.5 calls new-head writes “unchanged” although D11 adds PUT-first for unknown keys. The §8 claims that queue drops and SSE gaps were *silent* are inaccurate: the baseline logs queue drops and reconnect causes, though it does not log a structured gap interval. Evidence: [DESIGN.md:128](docs/DESIGN.md:128), [DESIGN.md:343](docs/DESIGN.md:343), [DESIGN.md:690](docs/DESIGN.md:690), [entity_utils.py:160](src/objectApps/correlators/entity_manager/entity_utils.py:160), [entity_utils.py:242](src/objectApps/correlators/entity_manager/entity_utils.py:242). **Recommendation:** align these summaries with D10/D11 and describe D9 as *structured gap accounting*. The other §8 bug claims check out: skipped Kalman rows shift `zip` pairing for `reportIds`; truncated preload can cause a full-record upsert; an equal-time duplicate can update the fuser again; and failed head creates drop that cycle’s events. [entity_tracker.py:1105](src/objectApps/correlators/entity_manager/entity_tracker.py:1105), [entity_tracker.py:1502](src/objectApps/correlators/entity_manager/entity_tracker.py:1502), [entity_fusion_filter.py:308](src/objectApps/correlators/entity_manager/entity_fusion_filter.py:308)

The historical backfill mention in the review-history row is followed by its removal; the operative D9 text consistently says **no backfill**. I found no broken section numbering or cross-reference.
